Most Tapix problems come from the queue, storage, or database setup, not from your importer. Find your symptom below.

## Queue and Workers

::accordion
  :::accordion-item{label='Why is my import stuck validating or never finishing?'}

The wizard shows *"Validation could not be completed"* / *"No background worker picked up the validation jobs"*, or the import never leaves the importing state.

Validation, match resolution, and execution all run as queued jobs. Check, in order:

1. **A worker is running.** `php artisan queue:work` (or Horizon) must be running for the connection in `QUEUE_CONNECTION`.
2. **The worker listens on Tapix's queues.** Jobs go to the queue names in `tapix.queue.validation` and `tapix.queue.execution` (both `'default'` out of the box). If you changed them, include them:

   ```bash [Terminal]
   php artisan queue:work --queue=default,imports-validation,imports
   ```

   With Horizon, add them to the supervisor's `queue` list.
3. **Your published config doesn't use the connection name as a queue name.** Configs published before v1.4.3 contain this:

   ```php [config/tapix.php]
   // Wrong: queue.default is a connection name (e.g. "redis"), not a queue
   'validation' => env('TAPIX_QUEUE_VALIDATION', config('queue.default')),
   ```

   Jobs then land on a queue literally named `redis` or `database` that no worker reads. Replace it with:

   ```php [config/tapix.php]
   'validation' => env('TAPIX_QUEUE_VALIDATION', 'default'),
   'execution' => env('TAPIX_QUEUE_EXECUTION', 'default'),
   ```

   Published config files never update with the package, so diff yours against the [Configuration](/getting-started/configuration) reference after upgrading.

4. **Web and workers share a cache.** Workers report validation progress through the default cache store, and the wizard reads it from the web process. With `CACHE_STORE=array`, or `file` on separate machines, the wizard never sees progress and reports a stall even though validation finished. Use `redis`, `database`, `memcached`, or `dynamodb`.

The wizard reports a stall when no progress arrives within 20 seconds. On busy queues, raise it:

```php [config/tapix.php]
'review' => [
    'stall_timeout_seconds' => 60,
],
```

  :::

  :::accordion-item{label='Why is my import marked failed when the rows were saved?'}

`no such table: notifications` (SQLite), `relation "notifications" does not exist` (PostgreSQL), or `Table '…notifications' doesn't exist` (MySQL) in `failed_jobs` or your logs.

When an import finishes, Tapix sends `ImportCompletedNotification` through the `database` channel. If the `notifications` table is missing, that call throws after all rows have been saved. The import is marked **failed**, the wizard shows an error, and the job is retried until it lands in `failed_jobs`. With `store.remote_disk` set, each retry starts over and creates the rows again.

Create the table:

```bash [Terminal]
php artisan make:notifications-table
php artisan migrate
```

Or turn notifications off:

```php [config/tapix.php]
'notifications' => [
    'enabled' => false,
],
```

  :::

  :::accordion-item{label='Why do I get a "job_batches table not found" error?'}

`no such table: job_batches` (SQLite) or `relation "job_batches" does not exist` (PostgreSQL).

Tapix dispatches its jobs with `Bus::batch()`, even on the `sync` connection. Create the batches table:

```bash [Terminal]
php artisan make:queue-batches-table
php artisan migrate
```

  :::

  :::accordion-item{label='Why do jobs run twice or create duplicate rows?'}

Your queue connection's `retry_after` is shorter than `tapix.queue.timeout` (600 seconds by default). Laravel's stock `retry_after` is 90, so the worker releases a long-running import job back onto the queue while the first attempt is still running.

Set `retry_after` to at least `queue.timeout + 30` on the connection Tapix uses:

```php [config/queue.php]
'redis' => [
    // ...
    'retry_after' => 630,
],
```

::::warning
With `store.remote_disk` set, a retried execution job starts again from the first row, and rows created by the failed attempt are created again. Keep `retry_after` above `timeout`, and make sure execution jobs aren't killed by your host's worker timeout.
::::

  :::

  :::accordion-item{label='Can I run imports on the sync queue?'}

`QUEUE_CONNECTION=sync` works for local development, but:

- The whole import runs inside the HTTP request, so PHP's `max_execution_time` and proxy timeouts apply, and `queue.timeout` is ignored.
- The delayed job that deletes each import's temporary store is skipped. Schedule `tapix:cleanup` so stores don't pile up:

  ```php [routes/console.php]
  Schedule::command('tapix:cleanup')->daily();
  ```

Use a real queue in production.

  :::
::

## Storage and Multiple Servers

::accordion
  :::accordion-item{label='Why does my import complete with 0 rows created?'}

This happens when web and queue workers run on different machines or containers (Laravel Cloud, Vapor, Kubernetes, separate worker servers) without a shared store.

Each import's rows are staged in a SQLite file under `store.path` on the local disk. A worker on another machine can't see that file, so it finds nothing to import. Point both web and workers at a shared disk:

```env [.env]
TAPIX_STORE_DISK=s3
```

The value must be identical on web and worker environments, and so must the disk's `filesystems.disks.*` config (same bucket). Otherwise workers fail with `SnapshotException: Remote import store snapshot is missing`.

When a remote disk is set, Tapix serializes writes with cache locks. Use a cache store that is shared across machines (`redis`, `database`, `memcached`, or `dynamodb`). `file` and `array` locks don't coordinate across servers.

  :::

  :::accordion-item{label='Why do I get "Tapix::disk(): filesystems disk is not defined"?'}

`TAPIX_STORE_DISK` names a disk that isn't in `config/filesystems.php`, or its driver isn't installed. For S3, install the adapter:

```bash [Terminal]
composer require league/flysystem-aws-s3-v3 "^3.0"
```

  :::

  :::accordion-item{label='Why do I get "WriteLockException: Could not acquire write lock"?'}

This only happens when `store.remote_disk` is set (multiple servers).

**What's going on:** each import's rows live in one SQLite file on the shared disk. To stop two jobs from overwriting each other's changes, a job must take a *lock* on the import before changing that file, and release it when done. Any other job that wants the same import waits for the lock.

The error means a job waited for the lock, gave up, and failed. That usually happens when two jobs work on the **same import** at once, for example when you run several queue workers and validation and match resolution land on different workers.

Two settings control this:

| Setting | Default | What it means |
|---------|---------|---------------|
| `store.lock.block_seconds.job` | `10` | How long a job **waits** for the lock before giving up with this error. |
| `store.lock.ttl` | `120` | How long a lock **lasts** before it expires on its own. This is a safety net so a crashed worker can't block an import forever. |

**Fix:**

1. **Let jobs wait longer.** Raise `block_seconds.job` so a job waits for the other one to finish instead of failing.
2. **Make the lock last as long as a job can run.** The lock isn't renewed while a job runs. A large import can run up to `queue.timeout` (600 seconds), but the default lock expires after 120. The lock can then run out mid-import, and another job can take it and change the same file. Set `ttl` to at least `queue.timeout`.

```php [config/tapix.php]
'store' => [
    'lock' => [
        'ttl' => 630,                      // >= queue.timeout (600) + a margin
        'block_seconds' => ['job' => 60],  // wait up to 60s instead of 10s
    ],
],
```

  :::

  :::accordion-item{label='Why do I get "could not find driver" during upload?'}

Import rows are always staged in a per-import SQLite database, whatever your main database is. Install the `pdo_sqlite` PHP extension on web and worker servers, and make sure `store.path` and `store.read_cache_path` are writable.

  :::

## Uploads

::accordion
  :::accordion-item{label='Why is my upload rejected below max_file_size?'}

The effective limit is the **smallest** of:

- `tapix.max_file_size` (50 MB)
- PHP's `upload_max_filesize` and `post_max_size`
- With `tapix/livewire`: Livewire's temporary upload rule, which defaults to 12 MB. Raise it in `config/livewire.php`:

  ```php [config/livewire.php]
  'temporary_file_upload' => [
      'rules' => ['required', 'file', 'max:51200'], // KB
  ],
  ```

`max_file_size` is enforced by the wizard UIs only. Programmatic `createFromFile()` calls don't check it.

  :::

  :::accordion-item{label='How do I import more than 100,000 rows?'}

Raise `tapix.max_rows`. The upload step reads the whole file into memory, so very large files can also hit PHP's `memory_limit` in the web request. Raise both together.

  :::

  :::accordion-item{label='Why do rows import blank or lose accented characters?'}

Tapix expects UTF-8. Rows that aren't valid UTF-8 (common with Excel's "CSV" export on Windows, which uses Windows-1252) are stored empty. Ask users to export as **CSV UTF-8**, or upload `.xlsx` instead.

  :::
::

## PostgreSQL and MySQL vs SQLite

SQLite accepts almost any value in any column. Importers that work in local SQLite tests can fail on PostgreSQL or strict MySQL. Failing rows land in `tapix_failed_import_rows` with the SQL error.

::accordion
  :::accordion-item{label='Why do I get "invalid input syntax for type integer" on PostgreSQL?'}

A field without a `type()` is treated as text, and text fields keep empty strings. Mapping an untyped field to an integer, numeric, date, boolean, or uuid column sends `""` to the database:

- PostgreSQL: `SQLSTATE[22P02] invalid input syntax for type integer: ""`
- MySQL strict mode: `Incorrect integer value`
- SQLite: stored without complaint

Give the field a type. Typed fields turn blank cells into `null`:

```php [app/Importers/ProductImporter.php]
ImportField::make('stock')->type(FieldType::Number),
ImportField::make('price')->type(FieldType::Currency),
ImportField::make('active')->type(FieldType::Boolean),
```

  :::

  :::accordion-item{label='Why does matching fail on id or uuid columns?'}

When matching or linking relationships on an integer or uuid column, a value that isn't numeric or a valid uuid (`abc`, `#12`) makes PostgreSQL throw `invalid input syntax for type integer` / `uuid` and fail the job. MySQL and SQLite just find no match. Add a validation rule so bad values are caught at review time:

```php
ImportField::make('id')->rules(['integer']),
ImportField::make('external_id')->rules(['uuid']),
```

  :::

  :::accordion-item{label='Why does composite matching fail with "function lower(integer) does not exist"?'}

Composite matching compares `LOWER(TRIM(column))`, which PostgreSQL only allows on text columns. Put a text column first in `MatchableField::composite([...])`.

  :::

  :::accordion-item{label='Why does the same CSV match on MySQL but not on PostgreSQL?'}

Single-field matching is an exact comparison. MySQL's default `_ci` collations make it case-insensitive. PostgreSQL and SQLite are case-sensitive, so `ACME` won't match `Acme`. Normalize case on both sides, e.g. lowercase emails when saving and in `beforeFill`. Composite matching is always case-insensitive.

  :::

  :::accordion-item{label='Was my issue fixed in a newer version?'}

| Symptom | Fixed in |
|---------|----------|
| Records matched by integer ID treated as new / "product ID 2 not found" | v1.4.16 |
| `SQLSTATE[23502]` not-null violation when a required cell is skipped | v1.0.0 |
| `no such table: import_rows` / `database disk image is malformed` on cloud hosts | v1.3.0 |
| `data.sqlite does not exist` 500 on the `sync` queue | v1.4.1 |

  :::

## Users and Migrations

::accordion
  :::accordion-item{label='Why does the user_id insert fail when my users have UUID or ULID keys?'}

The `tapix_imports` migration uses `foreignId('user_id')`, which assumes integer user IDs. If your users table uses UUIDs or ULIDs, publish the migrations before the first `migrate` and change the column:

```bash [Terminal]
php artisan vendor:publish --tag=tapix-migrations
```

```php [database/migrations/xxxx_create_tapix_imports_table.php]
$table->foreignUuid('user_id')->constrained()->cascadeOnDelete();
```

For programmatic imports without a logged-in user (CLI, scheduled tasks), always pass the user ID:

```php
Tapix::import(ContactImporter::class)->createFromFile($path, userId: $user->id);
```

  :::

  :::accordion-item{label='Why do I get duplicate table errors after publishing migrations?'}

Tapix loads its migrations automatically. Publishing them as well means Laravel sees two copies. Only publish if you need to change them, then run `migrate` once. Published copies don't receive migrations added in later releases, so check the changelog when upgrading.

  :::

  :::accordion-item{label='Why did my translations stop applying after an upgrade?'}

Core messages moved from the `tapix` to the `tapix-core` translation namespace. Re-publish with `--tag=tapix-core-translations` and move your overrides to `lang/vendor/tapix-core`.

  :::

## Multi-Tenancy

::accordion
  :::accordion-item{label='Why do I get TenantContextMissingException?'}

*"Job dispatched without tenant context while tenancy is enabled."* With `tenant.strict` on, every import job needs a tenant. Set the tenant before starting the import (see [Multi-Tenancy](/features/multi-tenancy)), or disable strict mode.

  :::

  :::accordion-item{label='Why is the imports list empty, or why do jobs throw ModelNotFoundException?'}

In strict mode, `Import` queries without a tenant context return no rows. Make sure your tenant resolver runs in the request and in queued jobs.

  :::

  :::accordion-item{label='Why do I get "column tenant_id does not exist"?'}

The tenant column is only created if `tenant.enabled` was `true` when the Tapix migrations ran. If you enabled tenancy later, add the column yourself:

```php [database/migrations/xxxx_add_tenant_id_to_tapix_tables.php]
Schema::table('tapix_imports', fn (Blueprint $table) => $table->string('tenant_id')->nullable()->index());
Schema::table('tapix_failed_import_rows', fn (Blueprint $table) => $table->string('tenant_id')->nullable()->index());
```

  :::
